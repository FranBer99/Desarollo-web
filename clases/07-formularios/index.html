Clase 07

Formularios

Los formularios son la puerta de entrada de los datos: permiten buscar, registrarse, inscribirse, opinar y pagar. Un formulario bien construido se puede completar con teclado, con lector de pantalla y desde un celular.

Objetivos
  • Comprender el circuito entre el formulario y el servidor.
  • Estructurar formularios con form, fieldset y label.
  • Elegir el campo adecuado para cada tipo de dato.
  • Aplicar validación nativa y estilos accesibles.

¿Qué es un formulario?

Un formulario es un conjunto de controles que permite al usuario ingresar datos y enviarlos a un servidor. El navegador recolecta los valores de los campos con atributo name, los codifica y los envía según el método indicado en method.

El servidor recibe esos datos, los valida y responde con una página nueva, una redirección o un error. HTML se ocupa de la interfaz y de la validación del lado del cliente; la validación definitiva y la seguridad siempre corresponden al servidor.

GET y POST

Métodos de envío
Método Dónde van los datos Cuándo usarlo
GET En la URL, después de ?. Búsquedas y filtros. Los datos quedan visibles en el historial.
POST En el cuerpo de la solicitud. Altas, modificaciones, datos personales o archivos.
dialog No se envía: cierra un dialog. Formularios dentro de un diálogo modal.

Nunca uses GET para contraseñas, datos personales o acciones que modifican información: la URL queda en el historial, en los registros del servidor y en el encabezado Referer.

El atributo name es el que viaja

El servidor recibe pares name=valor. Un campo sin name no se envía; un campo con disabled tampoco. El id sirve para asociarlo con el label; el name, para identificarlo en el envío.

Estructura del formulario

Un formulario se organiza en bloques lógicos. Cada bloque se envuelve en un fieldset con un legend que lo describe. Los controles se asocian a su etiqueta con label.

  • No anides formularios: un form dentro de otro es inválido.
  • Una etiqueta por control: label for debe coincidir con el id del campo.
  • Agrupá los campos relacionados con fieldset y legend.
  • Ordená los campos en el mismo orden en que se completan y en el que se leen.
  • Ubicá el botón de envío al final, salvo que el formulario sea muy largo.
El placeholder no es una etiqueta

El texto de placeholder desaparece al escribir, no se lee siempre con lectores de pantalla y suele tener poco contraste. Usalo solo como ejemplo de formato (“DD/MM/AAAA”), nunca para indicar qué dato va en el campo.

Campos de entrada

input es un elemento vacío cuyo comportamiento cambia según el atributo type. Elegir el tipo correcto mejora el teclado del celular, la validación y la accesibilidad.

Tipos de input más usados
Tipo Para qué Detalle
textTexto corto de una línea.Con maxlength y pattern si hace falta.
emailCorreo electrónico.Valida el formato y abre el teclado adecuado.
passwordContraseñas.Oculta lo que se escribe; no reemplaza el cifrado en tránsito.
searchBúsquedas.Puede mostrar un botón para limpiar.
telTeléfonos.No valida el formato: usá pattern si lo necesitás.
urlDirecciones web.Exige un esquema válido.
numberCantidades numéricas.Con min, max y step. No sirve para teléfonos ni tarjetas.
rangeValor dentro de un intervalo.Se usa con min, max y step.
date, timeFechas y horas.El navegador muestra un selector nativo.
colorColor.Devuelve un valor hexadecimal.
fileArchivos.Requiere enctype="multipart/form-data" en el formulario.
checkboxOpciones múltiples independientes.Cada opción lleva su propio name o el mismo con [] según el backend.
radioUna opción entre varias.Todas comparten el mismo name y van en un fieldset.
hiddenDatos internos.No es seguro: el usuario puede verlo y modificarlo.

Atributos de validación

  • required: el campo es obligatorio.
  • minlength y maxlength: longitud del texto.
  • min, max y step: rangos numéricos y de fecha.
  • pattern: expresión regular para el formato (por ejemplo, [0-9]{8}).
  • readonly: se puede leer, no modificar y sí se envía.
  • disabled: no se puede usar ni enviar.
  • autocomplete: ayuda al navegador a completar (por ejemplo, name, email, postal-code).
  • inputmode: sugiere el teclado adecuado sin cambiar el tipo.
La validación del navegador es una ayuda

Los atributos required, pattern y min mejoran la experiencia, pero se pueden saltar. El servidor debe validar todo de nuevo, con las mismas reglas y con mensajes claros.

Listas desplegables y áreas de texto

select

Una lista desplegable se construye con select, option y, opcionalmente, optgroup para agrupar. La primera opción suele ser una invitación a elegir, con value="" y disabled.

Con multiple se pueden elegir varias opciones, pero el control se vuelve más difícil de usar y no conviene para listas largas. En ese caso, un grupo de checkbox suele ser más claro.

datalist

datalist ofrece sugerencias mientras se escribe, sin obligar a elegir una. Se vincula con el atributo list del input. Es útil para ciudades, carreras o etiquetas.

textarea

Para textos largos se usa textarea, con rows y cols como tamaño inicial. El contenido va entre las etiquetas de apertura y cierre, no en un atributo value.

Botones

El elemento button es la forma correcta de crear un botón. Su atributo type define qué hace:

Tipos de botón
Tipo Acción
submitEnvía el formulario. Es el valor predeterminado si se omite type.
resetRestaura los valores iniciales. Casi nunca es una buena idea: se pierde lo escrito.
buttonNo hace nada por sí solo; requiere JavaScript.
Declará siempre el type

Un <button> sin type dentro de un formulario se comporta como submit. Si querés un botón secundario que no envíe nada, escribí type="button".

Para enviar a distintas direcciones desde un mismo formulario se usan formaction y formmethod en el botón. Para deshabilitar el envío mientras se procesa, se usa disabled, pero hay que explicar por qué con un mensaje visible.

Estilizado de formularios

Los controles nativos tienen apariencias distintas en cada navegador y sistema operativo. CSS permite unificar la presentación sin perder la funcionalidad ni la accesibilidad.

  • Usá font: inherit para que los controles no cambien de tipografía.
  • El foco debe verse siempre; no lo elimines sin reemplazo.
  • :user-invalid marca el error recién después de que la persona interactuó; :invalid se activa al cargar y confunde.
  • accent-color cambia el color de checkboxes y radios sin reimplementarlos.
  • No ocultes las etiquetas: si el diseño exige etiquetas visibles solo para lectores, usá la clase .visualmente-oculto con cuidado y un placeholder que no reemplace la información.
  • Los mensajes de error deben ser texto visible, no solo un borde rojo.

Accesibilidad

  • Cada control tiene una label visible asociada por for e id.
  • Los grupos de radios y checkboxes van dentro de un fieldset con legend.
  • Los campos obligatorios se indican en el texto (“Requerido”), no solo con color o un asterisco sin explicación.
  • Las ayudas y los errores se asocian con aria-describedby; si el error es de formato, se marca el campo con aria-invalid="true".
  • El orden de tabulación sigue el orden visual y lógico.
  • Los controles tienen un tamaño táctil suficiente (mínimo 24 × 24 px).
  • El botón de envío dice qué hace (“Inscribirme”, no “Enviar”).
  • No uses CAPTCHA inaccesibles ni bloquees el pegado de contraseñas.
  • Probá el formulario con teclado, con zoom al 200 % y con un lector de pantalla.

Actividad práctica

Crear el formulario de inscripción a un taller de la facultad.

  1. Armar dos fieldset: “Datos personales” y “Preferencias de cursada”.
  2. Incluir nombre, correo, teléfono, fecha de nacimiento y un selector de carrera.
  3. Agregar un grupo de radios para el turno y otro de checkboxes para los temas de interés.
  4. Agregar una textarea para consultas y un checkbox obligatorio de aceptación.
  5. Usar required, type y autocomplete donde corresponda; no usar placeholder como etiqueta.
  6. Estilizar con CSS manteniendo el foco visible y el contraste.
  7. Probar el envío con campos vacíos, con un correo inválido y con todo completo.
  8. Recorrer el formulario solo con Tab y comprobar que se entiende cada campo.

Para entregar: el HTML, el CSS y una lista de las validaciones aplicadas con el mensaje que ve el usuario en cada caso.

Resumen

  • El formulario envía pares name=valor al servidor según action y method.
  • GET va en la URL; POST, en el cuerpo y es el adecuado para datos sensibles o cambios.
  • fieldset y legend agrupan; label asocia cada control con su nombre.
  • El tipo de input correcto mejora la validación, el teclado y la accesibilidad.
  • La validación del navegador es una ayuda; el servidor debe validar de nuevo.
  • button type="submit" envía; type="button" no hace nada sin JavaScript.
  • Los errores se comunican con texto y se asocian al campo, no solo con color.
